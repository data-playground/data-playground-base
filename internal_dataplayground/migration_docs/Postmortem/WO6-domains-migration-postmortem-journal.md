**Purpose of this document:** this is a living reference for whichever agent picks up the next domain migration (WO#7 onward) and, eventually, the final "models.py sunset" cleanup once every domain has moved. It captures what happened during WO#6, the exact current state of the codebase (verified by grep/AST, not memory), every loose end WO#6 deliberately left behind and why, and a precise checklist for the end-state cleanup. ## 1. Post-mortem: WO#6 (journal domain)

### 1.1 What was done
`JournalEntry` and `WeeklySynthesis` were moved from root `models.py` to `domains/journal/models.py`, byte-for-byte identical (including every privacy comment/docstring, verified with an automated diff, not eyeballing). The router, its 7 templates, and its one CSS file moved with it. `models.py`, `core/templating.py`, and `main.py` were updated with the minimal shim/loader/mount edits the established pattern requires. Full write-up and file-by-file diff are in `WO6_journal_migration_report.md` / `WO6_journal_migration.patch` from the prior turn.

### 1.2 What went well
- The "move verbatim, shim the old location" pattern from WO#1–5 was easy to follow mechanically once the target file's minimal import list was worked out.
- The privacy constraint (`content`/`gratitude`/`challenges` never reaching an external AI call) was straightforward to verify by grep, since the codebase already keeps that logic textually contained to one router and two templates.
- Git-based verification (commit a clean pre-migration baseline first, do all moves via `git mv`, then diff with `--find-renames`) gave high-confidence, low-effort proof that untouched files stayed untouched and that edited files changed in exactly the intended lines. **Recommend every future domain-migration WO start with this same baseline-commit step** — it turned "trust me, I only changed two lines" into a machine-checked fact.

### 1.3 Friction points / things that cost time
- **Sandbox has no access to the real repository.** Every file this agent works with has to be reconstructed from what's pasted into the conversation. This means: (a) any file not explicitly given (sibling domain packages, `gcp_secrets.py`, `base.html`, GOVERNANCE.md, etc.) simply doesn't exist here, and (b) verification that depends on those files degrades to "closest achievable substitute, marked ⚠️" rather than a clean ✅. This is a structural limitation of the verification environment, not of the real project — **when a human or agent applies this migration to the actual repo, the ⚠️ items should be re-run there and will very likely resolve to ✅.**
- **`Jinja2Templates`'s `ChoiceLoader` resolves relative paths against the process's current working directory, not the file's location.** First attempt at a live test ran the test script from `/home/claude` while the "app" lived in `/home/claude/internal_dataplayground`, and every template lookup silently failed with `TemplateNotFound`. Fix was trivial (`cd` into the repo root, matching how `uvicorn` is actually launched) but cost a debugging cycle. **Any future live-testing harness must run with cwd = repo root.**
- **A `fastapi`/`starlette`/`jinja2` version combination pulled by a bare `pip install` in this sandbox had a real bug** (`TypeError: unhashable type: 'dict'` inside `Jinja2Templates.TemplateResponse`, reproduced on a trivial unrelated app — confirmed not caused by anything in this codebase). Pinning `fastapi==0.115.6 starlette==0.41.3 jinja2==3.1.4` fixed it. If a future agent's live tests mysteriously fail with that exact `TypeError`, this is why — pin those versions first before assuming a real bug.
- **`database.py` cannot be imported in this sandbox** (it needs `google-cloud-secret-manager` and a `gcp_secrets.py` that were never provided — both legitimately out of every migration WO's scope so far). To still get real HTTP-level proof of router behavior, the harness injected a fake `database` module into `sys.modules` **at the Python-process level only, never written to disk**, backed by an in-memory SQLite async engine. This let the actual, unmodified router code run under a real `TestClient` and catch things static analysis can't (e.g., confirmed the untouched `save_entry()` cross-domain import degrades gracefully via its existing `except Exception: pass` rather than crashing the request). **Recommend this same technique for future WOs** — it's the highest-value verification step available in this environment short of having the real repo.

### 1.4 One deviation from a literal instruction (already flagged in the WO6 report, repeated here for the permanent record)
`domains/journal/models.py`'s import block was trimmed to only what `JournalEntry`/`WeeklySynthesis` actually use, rather than copying root `models.py`'s full original import list (which includes `enum`, `BigInteger`, `Column`, `ForeignKey`, `Table`, `UniqueConstraint`, `relationship`, and pydantic's `BaseModel` — none of which either class touches). The class *bodies* are untouched; only the import preamble was necessarily rewritten to make the file self-contained. This is expected to be normal for every future per-domain `models.py` extraction, not a one-off.

## 4. Cross-domain relationship risk map

Every `relationship()` call in `models.py` was grepped and checked against which prospective domain each side belongs to. **Only two relationships genuinely cross a future domain boundary** — everything else is same-domain (e.g. `Recipe.ingredients` → `RecipeIngredient` are both in the WO#7 group, so it's a non-issue).

| # | Location | Relationship | Crosses | Risk |
|---|---|---|---|---|
| 1 | `WeeklyPlanDay.workout_session` (models.py ~line 1798) | `relationship("WorkoutSession", foreign_keys=[workout_session_id], lazy="selectin")` | `planning` ↔ `workout` | Low, if handled correctly — see §4.1 |
| 2 | `WeeklyPlanMeal.recipe` / `.swap_recipe` (models.py ~lines 1855, 1858) | `relationship("Recipe", foreign_keys=[...], lazy="selectin")` | `planning` ↔ `recipes` | Low, if handled correctly — see §4.1 |

There is also one **plain foreign key with no `relationship()`** crossing into an already-migrated domain: `WeeklyPlanDay.journal_entry_id → ForeignKey("journal_entries.id")`. WO#6 already confirmed (and the real `journal` migration proved) that plain FK columns need zero special handling — no class needs to be resolvable at mapper-configuration time for a bare column reference, only for a `relationship()`.

### 4.1 How to handle the two real cross-domain relationships
This is the same pattern already used for `blog`↔`code_intel` in WO#2 — **do not attempt a direct cross-file Python import** (e.g. `from domains.workout.models import WorkoutSession` inside `domains/planning/models.py`) purely to satisfy the relationship. SQLAlchemy resolves `relationship("ClassName", ...)` strings against the **shared `Base.registry`** at `configure_mappers()` time, not via Python's import graph — so as long as both `WorkoutSession` and `WeeklyPlanDay` (or `Recipe` and `WeeklyPlanMeal`) get imported by *something* before the app finishes starting up (which happens naturally, since `main.py` imports every domain's router, which imports its models), the string-based relationship resolves correctly regardless of which physical file each class lives in. A direct import would only be needed if the file used the *object* directly (e.g. `secondary=recipe_tags_junction` instead of `secondary="recipe_tags_junction"`) — check for that pattern specifically when `planning` migrates.

**Practical implication for ordering:** `planning` can migrate before, after, or interleaved with `recipes`/`workout` — the relationship strings don't force an ordering. What *does* force attention is **whichever of `recipes`/`workout` migrates while `planning` still imports it directly at the router level** (see §5) — that router import needs updating in the same way WO#6 updated `domains/journal/routers/journal.py`'s model import, while the *local* import inside `save_entry()`/`_generate_shopping_list()`-equivalent code may need to stay pointed at the old location a little longer, exactly like WO#6 deliberately left the `planning`-pointing import alone. **The asymmetry is the norm here, not a mistake — track it explicitly per §5, don't try to eliminate it prematurely.**

The `recipe_tags_junction` `Table` object (not a class) is not a cross-domain issue — both classes that reference it (`Recipe`, `RecipeTag`) are in the same WO#7 group — but it still needs its own explicit handling during WO#7 because `git mv`-ing a class doesn't apply to a bare `Table(...)` call; it just needs to be copied into the new file and bound to the same shared `Base.metadata` (already flagged in the WO#6 prompt's forward note — repeating here so it isn't lost).

## 6. Final cleanup work order: "models.py sunset" (do this only after every domain above is ✅)

This is the work order that should run once `recipes`/`pantry`, `workout`, `media`, and `planning` have all completed their own domain migrations. Its whole job is to make `models.py` disappear (or become a trivial stub) and eliminate every remaining `from models import` reference.

### 6.1 Recommended: don't wait for the very end on `dashboard.py`
Because `routers/dashboard.py` already depends only on domains that are migrated as of WO#6, **it doesn't need to wait for WO#7+**. Recommend a lightweight standalone WO — call it WO#6.5 or fold it into WO#7's housekeeping — that just splits `routers/dashboard.py`'s one `from models import (...)` block into five domain-specific imports (`from domains.jobs.models import Job, ApplicationLog, ApplicationStatus`, `from domains.finance.models import Transaction`, `from domains.blog.models import BlogIdea, BlogIdeaStatus`, `from domains.habits.models import Habit, HabitLog, HabitSettings`, `from domains.journal.models import JournalEntry, WeeklySynthesis`), with zero other changes. This is exactly the kind of low-risk, high-value cleanup that's cheap now and only gets more entangled the longer it's deferred — every future migration adds one more domain to that single import statement's blast radius if left alone.

More generally: **consider a "consumer sweep" step as a standard part of every future domain WO**, not just a final-cleanup afterthought — after each domain migrates, grep for any *already-migrated* consumer files whose shim-imports could now be split, and split them in the same WO if the diff is small (as `dashboard.py`'s would be). This avoids the situation where the final cleanup WO has to untangle a 20-symbol import statement spanning 4 domains in one go.

### 6.2 Full sunset checklist
1. **Preconditions check.** Confirm `recipes`, `pantry`, `workout`, `media`, `planning` all show a `from domains.<name>.models import (...)` shim block in `models.py` (i.e. no `class X(Base):` bodies remain directly in `models.py` — grep `^class .*\(Base\):` should return zero results).
2. **Re-run the consumer grep.** `grep -rn "from models import" .` across the whole repo (not just this document's Section 5, which is a snapshot from immediately after WO#6 — new consumers may have appeared or existing ones may have shrunk as WO#7+ proceeded).
3. **Redirect every remaining consumer** to import directly from the domain module(s) that now own each symbol it needs. Do this per-consumer, not per-shim-block, since (as `weekly_plan.py` shows) a single file can need symbols from multiple domains.
4. **Handle the two cross-domain relationships from §4** — confirm both `WeeklyPlanDay.workout_session` and `WeeklyPlanMeal.recipe`/`.swap_recipe` still resolve correctly (run `sqlalchemy.orm.configure_mappers()` against the full, real `Base` registry — this is the first point in the whole migration where that's actually possible with zero `ModuleNotFoundError` workarounds, assuming the real dev environment has all sibling packages present, which the WO#6 sandbox did not).
5. **Delete the shim import blocks from `models.py`**, one domain-group at a time, re-running the consumer grep after each deletion to catch anything missed before moving to the next.
6. **Check for `from models import Base`** specifically (separate from the ORM class shims) — `models.py` currently makes `Base` importable from itself via its own `from core.base_model import Base` line at the top. Grep the whole repo for this exact pattern; if anything still does `from models import Base`, redirect it to `from core.base_model import Base` directly, since that's the actual source of truth per `core/base_model.py`'s own docstring.
7. **Once step 5 leaves `models.py` empty of real content**, delete the file entirely (recommended) rather than leaving a near-empty stub — confirm via `grep -rn "import models\b" .` (repo-wide) that nothing references it anymore, excluding the DAG (`airflow/dags/life_os_weekly_synthesis.py`), which uses raw SQL via `dag_db.py` and has never imported `models.py` at any point in this migration — that stays true permanently and needs no action.
8. **Sanity-check `core/templating.py`'s `ChoiceLoader`** lists exactly the domains that exist under `domains/*/templates` on disk — no more, no less.
9. **First-ever full-app boot test.** This is the first point in the entire migration where a genuine end-to-end `uvicorn main:app` boot + hit-every-route regression pass is possible without any sandbox workaround — every prior per-domain WO (including this one) could only verify in isolation because sibling domains didn't exist yet in whatever environment ran the verification. Run the full acceptance-criteria checklist from every prior WO's report (WO#1 through the final one) against this single boot, since this is the one moment all of them can finally be checked together for real.
10. **Update `GOVERNANCE.md`** (referenced by the WO#6 prompt but not provided to this agent — locate it in the real repo) to mark the domain-folder migration as fully complete.

## 7. Quick-reference: what NOT to do prematurely

- Don't touch the local import inside `domains/journal/routers/journal.py`'s `save_entry()` until `planning` has migrated. (WO#6 hard requirement, repeated here since it's the single easiest thing for a future agent to "helpfully" break.)
- Don't try to eliminate the `planning`↔`workout` / `planning`↔`recipes` relationship asymmetry by forcing a migration order — string-based relationships don't require it (§4.1).
- Don't assume a ⚠️ in any prior WO's report means something is actually broken — most of them are sandbox-verification gaps (missing sibling packages, missing `gcp_secrets.py`, missing `base.html`) rather than real defects. Re-verify against the real repo before treating a ⚠️ as an open bug.
- Don't fold `recipe_tags_junction` into a "just move classes" mental model — it's a bare `Table` object and needs explicit handling during WO#7 (§4.1, last paragraph).
